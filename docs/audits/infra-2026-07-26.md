## Phase 3: CI/CD Pipeline Security

**Finding (MEDIUM, now fixed)**: no `.github/workflows/` existed at all prior to this audit — every verification in this project (fmt, clippy, tests, typecheck, lint, build) had been run manually, with no automated gate on pushes/PRs. Added a minimal `.github/workflows/ci.yml` covering `cargo fmt --check`/`clippy -D warnings`/`cargo test --workspace` and `pnpm typecheck`/`lint`/`test`/`build`, with `permissions: contents: read` (no broader token scope) and no `pull_request_target`. Devnet/E2E jobs (which need funded keypairs and take minutes) are intentionally **not** included in this CI — they stay a manual/scheduled concern, not a per-push gate.

## Phase 4: Shadow Infrastructure + Webhooks

- No inbound webhook endpoints exist anywhere in `apps/api` (`grep -rn "webhook"` returns nothing) — nothing to verify authenticity/replay-protection for.
- No hardcoded third-party domains/CDN endpoints/cloud resource IDs found outside the expected Solana RPC URLs (config-driven) and Explorer links (intentional, public).
- **Finding (LOW, deferred)**: `docker-compose.yml` references `infrastructure/docker/{api,indexer,web}.Dockerfile`, none of which exist — the `infrastructure/` directory itself is empty. `docker compose up postgres redis` (the only invocation any script in this repo actually uses) is unaffected; `docker compose up api indexer web` would fail. See `docs/SECURITY.md` SEC-06.
- Program upgrade authority: the deployed Devnet program's upgrade authority is the deployer keypair generated ad hoc for the original deploy (not a multisig) — acceptable for Devnet, called out explicitly as a pre-Mainnet requirement in `docs/security-audit-2026-07-26.md` and `docs/SECURITY.md`.
- RPC keys: `SOLANA_RPC_HTTP_URL` is server-side config only in `apps/api`/`apps/indexer`; the frontend's `NEXT_PUBLIC_SOLANA_*` vars intentionally carry no secret (network name + program ID only, both public by design).

## Phase 6: OWASP Top 10

| # | Category | Finding |
|---|----------|---------|
| A01 Broken Access Control | Every mutating route requires `AuthenticatedWallet` + `authz::require_org_member`/`has_one` checks (cross-referenced with `/audit-solana` for the on-chain equivalents) — no IDOR found in a spot-check of `events`/`checkpoints`/`participants` handlers, all resource lookups scope by the caller's own org/wallet. |
| A02 Cryptographic Failures | HS256 JWTs (HMAC, not weak), ed25519 signature verification for wallet auth (no roll-your-own crypto), no MD5/SHA1-for-security usage found. |
| A03 Injection | All SQL goes through `sqlx::query`/`query_as` with `.bind(...)` parameterization; the two `format!()`-built queries only interpolate compile-time column-list constants (verified, see Summary). No `dangerouslySetInnerHTML`/`innerHTML`/`eval`/`new Function` anywhere in `apps/web/src`. |
| A04 Insecure Design | Rate limiting active on the check-in flow (`checkins::handlers::check_rate_limit`, 10 req/60s per wallet). Auth `nonce`/`verify` endpoints have no explicit rate limit — noted as SEC-07 (low, deferred: nonce generation is cheap, and `verify` requires a valid ed25519 signature, which is itself a strong anti-flood cost). |
| A05 Misconfiguration | No CORS layer configured — the app relies on Next.js same-origin proxying by design (ADR-documented), so the *absence* of a permissive CORS policy is the secure default, not a gap. Session cookie is `HttpOnly` + `Secure` + `SameSite=Lax`. |
| A06 Vulnerable Components | See Phase 2. |
| A07 Auth Failures | Wallet auth: full SIWS-style message (domain + nonce + issued/expiration) signed over its exact rendered bytes, nonce is single-use via Redis `GETDEL` (verified in `auth/session.rs`), session TTL enforced. |
| A08 Integrity Failures | `packages/chain-client`/`crates/eventquest-chain` are both generated from the same built IDL (`/generate-idl-client`) — no manual duplicate account-layout definitions to drift. Upgrade authority: see Phase 4. |
| A09 Logging Failures | **Finding (MEDIUM, now fixed)**: `apps/api`'s `AppConfig.log_level` (parsed from `LOG_LEVEL`) was never actually wired into the `tracing_subscriber::EnvFilter` — the filter only ever read `RUST_LOG` (undocumented) and silently fell back to a hardcoded `"info"` otherwise, meaning `LOG_LEVEL` did nothing. Fixed in `apps/api/src/main.rs` and `apps/indexer/src/main.rs` to read `RUST_LOG` first, then `LOG_LEVEL`, then `"info"`. Separately, **finding (MEDIUM, now fixed)**: `TraceLayer::new_for_http()` was used with its default span, which records the full request URI *including query string* — several public routes (`qr-stream`, `current-qr`) carry a bearer-like `displayAccessToken`/QR token in the query string (required because `EventSource`/plain `GET` can't send custom headers), which spec §26 explicitly requires never be logged in full. Fixed in `apps/api/src/router.rs` with a custom `make_span_with` that only records `method` + `uri.path()`, never the query string. |
| A10 SSRF | The only server-side outbound HTTP calls are `apps/api`/`apps/indexer`'s Solana RPC clients, POSTing to `config.solana.rpc_http_url` — an operator-set config value, never influenced by request input. No user-controlled URL is ever fetched server-side. |

## Phase 7: STRIDE Threat Model

| Component | Threat | Mitigation | Gap |
|---|---|---|---|
| Frontend (wallet auth) | Spoofing | ed25519 signature over a nonce-bound message | none found |
| `apps/api` (check-in) | Tampering | On-chain `has_one`/PDA constraints are the final authority; DB state is advisory until the indexer confirms | none found |
| `apps/api` → chain | Repudiation | Every check-in is a signed, on-chain, Explorer-visible transaction with an emitted event | none found |
| `apps/api` (errors) | Info Disclosure | Structured `ApiError` responses use fixed error codes, not raw internal messages; now confirmed query strings aren't logged (see A09 fix) | none found |
| `apps/api` (check-in) | DoS | Rate limit on check-in attempts per wallet | auth `nonce`/`verify` unrated (SEC-07, low) |
| `apps/api` (authz) | Elevation of Privilege | `authz::require_org_member` gates every organizer action; on-chain `has_one = authority` is the ultimate backstop even if an off-chain check were ever bypassed | none found |

## Phase 8: Data Classification

- **PII**: none collected. Auth is wallet-address-only; no name/email/IP/government-ID field exists anywhere in the schema (`apps/api/migrations`) or on-chain accounts.
- **Financial**: none — no token transfers, no payment flows (explicitly out of MVP scope per spec §4/§30, and confirmed absent in the program's instruction set).
- **Auth material**: the attestor's private key lives only in a gitignored keypair file (`.secrets/attestor-devnet.json`), read once at process startup — never stored in Postgres/Redis, never logged, never sent to the frontend.
- **Regulated data**: none in scope.
